Sinas supports three authentication modes for end-user login, plus API keys for programmatic access. The mode is set per-deployment via the `AUTH_MODE` environment variable and cannot be changed at runtime.

## Auth Modes

| Mode | What's required to log in | When to use |
|---|---|---|
| `otp` (default) | Email + 6-digit OTP | Default. Proves email control on every login. Requires SMTP. |
| `password` | Email + password | Airgapped or no-SMTP deployments. No email round-trip. |
| `password+otp` | Email + password + OTP | Most secure. Treats the OTP as a liveness check on the email account — useful when you need to lock out ex-employees by revoking their work mailbox. Requires SMTP. |

Clients (custom frontends, the JS/Python SDKs, the official console) discover the active mode via the unauthenticated `GET /info` endpoint and branch their login UI accordingly. The same response carries `features` (what this instance has enabled) and `services` (what installed apps publish about themselves through their [manifest's `publicInfo`](/admin/manifests#publishing-on-info), such as the browser-reachable URL of a sibling service).

## Login Flows

### `otp`

1. Client posts email to `POST /auth/login`
2. Sinas sends a 6-digit code (valid 10 min by default)
3. Client posts code to `POST /auth/verify-otp` and receives access + refresh tokens

### `password`

1. Client posts email + password to `POST /auth/login`
2. Sinas verifies and immediately returns access + refresh tokens

### `password+otp`

1. Client posts email + password to `POST /auth/login`
2. On password match, Sinas sends a 6-digit OTP and returns an OTP session id
3. Client posts code to `POST /auth/verify-otp` and receives access + refresh tokens

## Tokens

All modes issue the same JWT pair:

- **Access token** — short-lived (default 15 min), sent as `Authorization: Bearer <token>`
- **Refresh token** — long-lived (default 30 days), exchanged at `POST /auth/refresh`

```
POST   /auth/login                # Start login (mode-dependent payload)
POST   /auth/verify-otp           # Verify OTP for otp / password+otp modes
POST   /auth/refresh              # Get new access token
POST   /auth/logout               # Revoke refresh token
GET    /auth/me                   # Get current user info
```

## Superadmin Bootstrap

The first admin user is seeded from environment variables on backend startup:

- `SUPERADMIN_EMAIL` — email of the user to create / promote to Admins
- `SUPERADMIN_PASSWORD` — only used when `AUTH_MODE` is `password` or `password+otp`. While set it is authoritative: it is applied on every boot, so setting it on a running deployment and restarting the backend resets the password (the escape hatch for "admin lost their password"), and a password changed in the console reverts. Leave it unset to let the superadmin choose their own with a [setup link](#setup-links); until they have, the backend logs on every boot how to mint one (never the link itself).

## Setup Links

A setup link is a one-time console URL, `<console>/ui?token=…`, with which someone sets their password and signs in. The first admin gets one from the operator; any user can get one from an admin.

**Minting**

- **Operator (CLI)**, inside the backend container: `python -m app.cli setup-link [--email …]` (default: `SUPERADMIN_EMAIL`). For example `docker compose exec backend python -m app.cli setup-link`, or `kubectl exec deploy/backend -c backend -- python -m app.cli setup-link`. Prints the full URL, built from the configured console URL (`CONSOLE_URL`, else `https://$DOMAIN/ui`).
- **Admin (console)** — the key icon on the Users page ("Generate password reset link") produces the same kind of link. API: `POST /api/v1/users/{id}/password-reset` (`sinas.users.update:all`).
- The installer runs the CLI at the end of a fresh install without `SUPERADMIN_PASSWORD` and prints the link once.

**Token rules.** 256 random bits, stored only as a SHA-256 hash, single use, valid for `PASSWORD_RESET_TOKEN_TTL_HOURS` (default 24). Minting a new link for a user revokes their earlier links and any setup session; setting or changing the password (by any route, including a pinned `SUPERADMIN_PASSWORD`) revokes all of them. A link and the setup session it is traded for are different kinds of token: only a link can be exchanged, only a session can complete setup, so a session never yields another session. All of this runs serialised per user (a row lock on the user), so a password change can't miss a session created at the same moment, and concurrent mints or exchanges leave exactly one usable token. Unknown, expired, used, replaced links and links for deactivated accounts all get the same response.

**The flow.** The console takes the token out of the address bar (`history.replaceState`) before it renders or fetches anything, and immediately trades it via `POST /auth/setup-link/exchange` for a short-lived setup session (30 minutes, kept in the tab). That spends the link: a copy in browser history or a log is useless once the person it was meant for has opened it. It also means a chat app that only fetches the page for a preview doesn't use it up; one that runs the page's JavaScript would. The page then shows **Set your password** (current password policy: 8 characters minimum, 72 bytes maximum). `POST /auth/setup-link/complete` sets it and signs in the way a correct password does in the current mode: tokens straight away for `password`, an emailed code first for `password+otp`. The link never skips the second factor.

**Accounts that already have a password.** A link is never a sign-in link on its own. Opened for an account that already has a password, it says so and offers **Sign in** normally; the person can instead choose a new password with it, which is what an admin's reset link has always been for. Only after a new password is saved does it sign them in.

**OTP-only mode** (`AUTH_MODE=otp`). Setup links aren't used: people sign in with the emailed code, and there is no password to set. The CLI and the admin endpoint refuse to mint one, and an older link shows "sign in with the code emailed to you". We deliberately don't let a link sign in directly here: that would make a 24-hour bearer URL a way in that skips proving control of the mailbox.

**Security.** The exchange and complete endpoints are rate limited per IP (`RATE_LIMIT_SETUP_LINK_IP_MAX` per `RATE_LIMIT_WINDOW_SECONDS`). Opening a link and setting a password are logged with the user id, never the token. Request logs mask `token`-style query parameters and Referers (names read as the browser reads them: percent-decoded, any case), request bodies of `/auth/*` are not logged, and the console's nginx access log drops query strings.

## Password Reset

For modes that include passwords:

- **User-initiated** — not implemented when `AUTH_MODE=password` (no email channel guaranteed). Use admin reset.
- **Admin-initiated** — an admin generates a one-time [setup link](#setup-links) from the user management page in the console and delivers it out-of-band (Slack, in person). The user chooses a new password with it.
- **Lost-superadmin escape hatch** — mint a setup link with the CLI (`python -m app.cli setup-link`), or set `SUPERADMIN_PASSWORD` in the env and restart the backend.

## API Keys

For programmatic access (scripts, CI/CD, integrations), create API keys instead of using short-lived JWT tokens. Each key has its own set of permissions (a subset of the creating user's permissions). API keys work identically across all auth modes.

```
POST   /api/v1/api-keys           # Create key (plaintext returned once)
GET    /api/v1/api-keys           # List keys
GET    /api/v1/api-keys/{id}      # Get key details
DELETE /api/v1/api-keys/{id}      # Revoke key
```

API keys can be used via `Authorization: Bearer <key>` or `X-API-Key: <key>` headers. Keys can have optional expiration dates.

A key acts with **its own** permissions everywhere, including through agents: when a chat is started or continued with a key, the agent's tools (functions, queries, stores, collections, sub-agents, pipelines) are checked against the key's live permissions, not its owner's — and so are components and artifacts shown in that chat. A key that may only chat with an agent can't use that agent's tools; grant the key those tools' permissions too. Revoking or narrowing a key takes effect immediately, also for runs already queued.

## Token Exchange (bring your own auth)

If your application already authenticates users itself, you don't need to run a second Sinas login flow. Your backend exchanges its knowledge of "who is logged in" for Sinas tokens:

1. An admin links your application's user ids to Sinas users as [external identities](/admin/users-roles#external-identities) — or you let the exchange auto-provision them.
2. Your backend calls the exchange endpoint with an API key holding the `sinas.auth.exchange:all` permission:

```json
POST /auth/token/exchange
X-API-Key: <exchange key>
{
  "provider": "acme-app",
  "subject": "usr_8f3a2",
  "email": "jane@acme.com",
  "metadata": {"name": "Jane"},
  "custom_fields": {"plan": "enterprise"},
  "auto_provision": true
}
```

3. The response contains a normal Sinas access + refresh token pair for that user, which your frontend uses against the runtime API. All ownership scoping (`:own`), permissions, and audit logging apply as if the user had logged in directly.

Behavior details:

- The user is resolved by `(provider, subject)`. If unknown and `email` is given, an existing user with that email is matched and the identity is linked to them.
- With `auto_provision: true`, unknown users are created and assigned the `TOKEN_EXCHANGE_DEFAULT_ROLE` (default `GuestUsers`). `email` is required to provision.
- `metadata` is stored on the identity and refreshed on every exchange. `custom_fields` is shallow-merged into the user's custom fields (partner keys win, admin-set keys survive).
- `provisioned: true` in the response indicates the exchange created the user.

The exchange endpoint trusts the caller to assert identities — treat keys with `sinas.auth.exchange:all` like any other admin credential.

## Verifying Tokens From Your Own Services

The reverse direction — your services validating Sinas tokens — works with standard JWT middleware once `JWT_ALGORITHM=RS256` is set: public keys at `/.well-known/jwks.json`, profile claims at `/userinfo`. See [Verifying Sinas Tokens](/platform/verifying-tokens).
