Agents are configurable AI assistants. Each agent has an LLM provider, a system prompt, and a set of enabled tools.

**Key properties:**

| Property | Description |
|---|---|
| `namespace` / `name` | Unique identifier (e.g., `support/ticket-agent`) |
| `llm_provider_id` | LLM provider to use (null = system default) |
| `model` | Model override (null = provider's default) |
| `provider_overrides` | Per-agent overrides of provider behavior settings, e.g. `{"prompt_caching": false}`. Absent key = inherit the provider's setting. Only whitelisted behavior keys are accepted; connection settings can't be overridden. Config key: `providerOverrides`. |
| `system_prompt` | Jinja2 template for the system message |
| `temperature` | Sampling temperature (default: 0.7) |
| `max_tokens` | Max token limit for responses |
| `input_schema` | JSON Schema for validating chat input variables |
| `output_schema` | JSON Schema for validating agent output |
| `initial_messages` | Few-shot example messages |
| `enabled_functions` | Functions available as tools. Supports wildcards: `namespace/*` or `*/*`. |
| `function_parameters` | Default parameter values per function (supports Jinja2) |
| `enabled_agents` | Other agents callable as sub-agents. Supports wildcards. |
| `enabled_skills` | Skills available to the agent. Supports wildcards. |
| `enabled_queries` | Database queries available as tools. Supports wildcards. |
| `query_parameters` | Default query parameter values |
| `enabled_collections` | File collections the agent can access. Plain string (readonly) or `{"collection": "namespace/name", "access": "readonly\|readwrite"}`. Supports wildcards. Readwrite enables write/edit/delete file tools. |
| `enabled_stores` | Stores the agent can access. List of `{"store": "namespace/name", "access": "readonly"}` or `{"store": "namespace/name", "access": "readwrite"}` |
| `enabled_connectors` | Connectors available as tools. List of `{"connector": "namespace/name", "operations": [...], "parameters": {"op_name": {"param": "value"}}}`. Parameters support Jinja2 templates and are locked (hidden from LLM). |
| `enabled_pipelines` | [Pipelines](/build-resources/pipelines) available as tools — only those marked `asTool`. Supports wildcards. Each becomes one semantic tool whose parameters are the pipeline's `inputSchema`. |
| `hooks` | Message lifecycle hooks. `{"on_user_message": [...], "on_assistant_message": [...]}` |
| `system_tools` | Platform capabilities. List of strings or config objects. See [System Tools](#system-tools). |
| `tool_approvals` | Permission mode: which tool calls run unattended and which stop for the user's approval. `{"default": "auto"\|"ask", "rules": [{"match": "<glob over tool name>", "action": "auto"\|"ask"}]}`, first matching rule wins. Config key: `toolApprovals`. See [Way of Working](/build-resources/way-of-working#tool-approvals). |
| `retention_days` | How long chats with this agent are kept after their last activity before they are archived and deleted: `null` = the deployment default, `0` = keep forever (`"never"` in config), `N` = N days. Only applies when the operator has switched [chat retention](/admin/chat-retention) on. Changing it takes `sinas.retention.update:all`. Config key: `retentionDays`. |
| `icon` | Icon reference (see [Icons](#icons)) |

**Wildcard patterns** for `enabled_*` fields:

| Pattern | Matches |
|---|---|
| `namespace/name` | Exact resource |
| `namespace/*` | All active resources in that namespace |
| `*/*` | All active resources |

```yaml
enabledFunctions:
  - sales/*          # all functions in the sales namespace
  - shared/utils     # one specific function
enabledQueries:
  - "*/*"            # all queries (quote wildcards in YAML)
enabledPipelines:
  - search/semantic  # an asTool pipeline, exposed as one tool
enabledMcpServers:
  - tools/tracker    # every tool an MCP server allows (see MCP Servers)
  - server: tools/docs
    tools: ["search_*"]
enabledCollections:
  - collection: "docs/*"
    access: readonly
```

Wildcards expand at tool discovery time. The resolved tools are validated against user permissions at execution time.

**Message hooks:** Functions that run before/after agent messages. Each hook has:
- `function`: reference to a function (`namespace/name`)
- `async`: if true, fire-and-forget (no impact on latency)
- `on_timeout`: `block` (stop pipeline) or `passthrough` (continue) — sync hooks only

Hook functions receive `{"message": {"role": "...", "content": "..."}, "chat_id": "...", "agent": {"namespace": "...", "name": "..."}, "user_id": "..."}` and can return:
- `{"content": "..."}` to mutate the message
- `{"block": true, "reply": "..."}` to stop the pipeline
- `null` to pass through unchanged

```yaml
agents:
  - name: my-agent
    hooks:
      onUserMessage:
        - function: default/guardrail
          async: false
          onTimeout: block
      onAssistantMessage:
        - function: default/pii-filter
          async: false
          onTimeout: passthrough
```

**Management endpoints:**

```
POST   /api/v1/agents                       # Create agent
GET    /api/v1/agents                       # List agents
GET    /api/v1/agents/{namespace}/{name}    # Get agent
PUT    /api/v1/agents/{namespace}/{name}    # Update agent
DELETE /api/v1/agents/{namespace}/{name}    # Delete agent
```

**Runtime endpoints (chats):**

```
POST   /agents/{namespace}/{name}/invoke             # Invoke (sync request/response)
POST   /agents/{namespace}/{name}/chats              # Create chat
GET    /chats                                        # List user's chats (pageable: ?limit, ?cursor)
GET    /chats/{id}                                   # Get chat with messages
PUT    /chats/{id}                                   # Update chat
DELETE /chats/{id}                                   # Delete chat
POST   /chats/{id}/messages                          # Send message
POST   /chats/{id}/messages/stream                   # Send message (SSE streaming)
GET    /chats/{id}/stream/{channel_id}               # Reconnect to active stream
POST   /chats/{id}/approve-tool/{tool_call_id}       # Approve/reject a tool call
GET    /chats/{id}/pending-input                     # Open ask_user questions
POST   /chats/{id}/pending-input/{tool_call_id}      # Answer one (add "wait": true for the result)
```

**Invoke endpoint:** A synchronous request/response alternative to the two-step chat flow. Intended for integrations (Slack, Telegram, webhooks) that need a simple call-and-response.

```bash
# Simple invoke
curl -X POST https://yourdomain.com/agents/support/helper/invoke \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"message": "What is the status of order #123?"}'
# → {"reply": "Your order is on its way...", "chat_id": "c_abc123"}

# With session key (conversation continuity)
curl -X POST https://yourdomain.com/agents/support/helper/invoke \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"message": "Follow up on that", "session_key": "slack:U09ABC123"}'
# → Same chat_id as previous call with this session_key
```

- `session_key`: Maps an external identifier (Slack channel, Telegram chat, WhatsApp number) to a persistent Sinas chat. One chat per `(agent_id, session_key)` pair.
- `reset: true`: Archives the existing session and starts a new conversation.
- `input`: Agent input variables, only used when creating a new chat.
- Streams internally, returns assembled reply as a single JSON payload.
- `usage`: the LLM usage of this invoke (see below).

**Usage per invoke.** The response's `usage` totals the LLM calls made to answer this invoke: the reply and every tool round before it. It doesn't include earlier invokes in the same `session_key` chat, so you can add it up per request without double counting.

```json
{
  "reply": "Your order is on its way...",
  "chat_id": "…",
  "session_key": "slack:U09ABC123",
  "usage": {
    "calls": 3,
    "prompt_tokens": 4100,
    "completion_tokens": 90,
    "total_tokens": 4190,
    "cache_read_tokens": 1500,
    "cache_write_tokens": 1500,
    "cost_usd": 0.0061,
    "unpriced_calls": 0,
    "errors": 0
  }
}
```

- The fields are the same as the metrics of [`/api/v1/usage/summary`](/admin/usage-cost#api). `prompt_tokens` includes the cache reads and writes.
- `cost_usd` adds up the calls that have a price. It's `null` when no call could be priced. When `unpriced_calls` is above 0, the cost covers only the priced calls. See [Usage & Cost](/admin/usage-cost) for setting prices.
- Each call is also an `llm_usage` row, saved before the response is sent, so `/api/v1/usage` reports agree with it right away. `cost_usd` only includes calls whose row was saved. If a row fails to save, or takes more than 10 seconds, that call still counts in `calls` and the token totals (it was made, and the provider bills it), but as unpriced, without its cost. In that rare case the tokens are higher than what `/api/v1/usage` has on record.
- Not included: calls made by sub-agents this agent delegates to (they run as separate jobs, in their own chats; query `/api/v1/usage/summary?chat_id=…` for those), and background history compaction.
- `usage` is `null` only if it couldn't be worked out.
- If the session's chat is already busy with another request, the message is queued into that run, `status` is `injected`, `reply` is empty and `usage` shows 0 calls: the reply's calls are counted on the request that runs them.
- If the agent waited on a background run (`run_in_background` with `wait: true`) and this request followed it to the reply, `usage` includes the calls made after the run finished. If the request runs out of time before the turn finishes (status `in_progress`), `usage` is `null`: the rest of the turn may already be making calls that can't be counted yet. Calls made after you answer a question are counted on the answer, when it waits for the result (see below).

`POST /chats/{id}/messages` (non-streaming) returns the same `usage` with the reply message.

#### When the agent asks or waits

An agent with `askUser` can stop a turn to ask the user a question, and one with `background` can wait for a background run (`run_in_background` with `wait: true`). The turn's tool round then parks until the answer or the result arrives, without holding a worker. This works however the turn was started. Each entry point says what the turn ended in:

| `status` | Meaning | What to do |
|---|---|---|
| `completed` | The final reply is in the response | — |
| `input_required` | The agent asked a question. The turn waits for the answer. `pending_inputs` lists the open questions (`tool_call_id`, `question`, `options`, `expires_at`) | Answer with `POST /chats/{id}/pending-input/{tool_call_id}` |
| `in_progress` | The turn goes on without this request: background work outlasted the request's time budget | Follow it on `channel_id` (`GET /chats/{id}/stream/{channel_id}`), or read the chat later |
| `injected` | The chat was busy, so the message was passed to the turn already running there (or parked on a question or background work). Nothing was answered here | `pending_inputs` and `channel_id` say what that turn waits on |

`POST /agents/{ns}/{name}/invoke` and `POST /chats/{id}/messages` carry `status`, `pending_inputs` and `channel_id`. With `input_required` or `in_progress`, `reply` (or the returned message) holds only what the agent said before it asked or started waiting, which is often nothing. A turn that waits on a background run is followed to its reply within the request: the agent's `default_job_timeout` for invoke, and the chat's job timeout for messages. Only a question, or running out of that time, ends the request early.

```json
{
  "status": "input_required",
  "reply": "",
  "chat_id": "…",
  "session_key": "slack:U09ABC123",
  "pending_inputs": [
    {"tool_call_id": "call_8f2…", "question": "Which order number?", "options": null, "expires_at": "…"}
  ],
  "channel_id": null,
  "usage": {"calls": 1, "…": "…"}
}
```

**Answering.** `POST /chats/{id}/pending-input/{tool_call_id}` with `{"answer": "…"}` makes the answer the question's tool result. If it was the last thing the turn waited for, the turn resumes on a new stream channel. The response is `202` with that `channel_id`, which you follow with `GET /chats/{id}/stream/{channel_id}`. Add `"wait": true` to get the resumed turn's result in the same response instead. That response is `200` and has the invoke shape above: `status`, `reply`, `message`, `pending_inputs`, `channel_id` and the `usage` of the resumed turn. If the agent asks again, it is `input_required` with the new question. Unanswered questions expire after `ASK_USER_TIMEOUT_SECONDS` (24 hours by default). The turn then resumes without an answer, and the agent is told the user didn't respond.

```bash
curl -X POST https://yourdomain.com/chats/$CHAT_ID/pending-input/call_8f2… \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"answer": "123", "wait": true}'
# → {"status": "completed", "reply": "Order 123 shipped yesterday.", …}
```

Sending another message to a chat that waits on a question doesn't answer the question. The message is `injected` and read once the turn resumes. The exception is the [OpenAI-compatible endpoint](/platform/api-overview), which can only send messages: there, the next message in the chat is the answer.

On a stream (`POST /chats/{id}/messages/stream`) the question arrives as an `input_required` event, followed by `round_suspended`, and the stream ends with `done` `{"status": "suspended"}`. A round waiting on a background run keeps the stream open and streams the rest of the turn when the run finishes. If that round also asked a question and you answer it while the stream is open, the stream follows the turn to the channel the answer resumed it on. This is the same for keep-alive and inline chats.

**How chat works:**

1. Create a chat linked to an agent (optionally with input variables validated against `input_schema`)
2. Send a message — Sinas builds the conversation context with the system prompt, preloaded skills, message history, and available tools
3. The LLM generates a response, possibly calling tools
4. If tools are called, Sinas executes them (in parallel where possible) and sends results back to the LLM for a follow-up response
5. The final response is streamed to the client via Server-Sent Events

**Thinking while it streams.** Reasoning models can think for several seconds before their first word. When the model starts thinking, the stream sends a `message` event with an empty `thinking` field (and no `content`). Use it to show that the model is working.

The thinking text itself is only sent when the client asks for it, with `"include_thinking": true` in the message body (or `?include_thinking=true` when reconnecting to a stream). It can mention things the answer leaves out, such as the system prompt or tool results, so only ask for it where the viewer may see those. The text arrives in `thinking` too. The OpenAI-compatible endpoints take the same `include_thinking` field and send the thinking as `delta.reasoning_content`. Where it comes from:

- **Anthropic** (the text only when the model shows it).
- **OpenAI-compatible servers** that send `reasoning_content` or `reasoning`, such as DeepSeek, vLLM, OpenRouter and Groq.
- **Mistral** reasoning models (Magistral).
- **Ollama** thinking models.

OpenAI's own API doesn't stream reasoning. Thinking is never saved with the message.

To spend less time thinking, lower it per agent: `provider_overrides: {"effort": "low"}` on Anthropic models that support effort. Claude Haiku 4.5 and Sonnet 4.5 reject it, so leave it out for agents on those models.

**Ephemeral chats** can be created with a TTL by passing `expires_in` (seconds) when creating the chat. Expired chats are automatically hard-deleted (with all messages) by a scheduled cleanup job:

```bash
# Create an ephemeral chat that expires in 1 hour
curl -X POST https://yourdomain.com/agents/default/default/chats \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"expires_in": 3600}'
```

**Chat archiving** — Chats can be archived via `PUT /chats/{id}` with `{"archived": true}`. Archived chats are hidden from the default list but can be included with `?include_archived=true`.

**Listing chats** — `GET /chats` returns the caller's own chats, most recently updated first, each with `last_message_at`. It takes these query parameters:

| Parameter | Default | Description |
|---|---|---|
| `include_archived` | `false` | Include archived chats |
| `q` | — | Only chats whose title contains this text (case-insensitive) |
| `limit` | — | Page size, 1–200. Passing `limit` or `cursor` turns on pagination |
| `cursor` | — | The `X-Next-Cursor` value of the previous page. Pages hold 50 chats unless `limit` says otherwise |

The body is a JSON array of chats either way. Without `limit` or `cursor`, every matching chat is returned in one response, as in earlier versions, up to `CHATS_UNPAGINATED_MAX` (default 10,000). That stays supported, but it is slow for accounts with many chats, so new clients should page. When paging, a response that has more chats after it carries the cursor for the next page in the `X-Next-Cursor` header, and the same next page as a relative URL in a `Link: <...>; rel="next"` header. The last page has neither header. Treat the cursor as opaque, and pass the same filters with it. An invalid cursor returns `400`.

An account with more than `CHATS_UNPAGINATED_MAX` chats gets only the most recently updated that many from an unpaginated request. The response then says so with `X-Truncated: true` and carries the same `X-Next-Cursor` and `Link` headers a page does, and the backend logs a warning. Continue from that cursor as you would from any page; the `Link` URL asks for pages of 200. A response without `X-Truncated` is the complete list.

```bash
# First page of 50
curl -i "https://yourdomain.com/chats?limit=50" -H "Authorization: Bearer $TOKEN"
# X-Next-Cursor: eyJ1IjoiMjAyNi0xMC0xOFQx...

# Next page
curl -i "https://yourdomain.com/chats?limit=50&cursor=eyJ1IjoiMjAyNi0xMC0xOFQx..." \
  -H "Authorization: Bearer $TOKEN"
```

Pages are keyset-based on `(updated_at, id)`. A chat that is created or updated while you page moves to the front of the list: later pages neither repeat nor skip the other chats, and the moved chat shows up when you fetch the first page again.

**Agent-to-agent calls** go through the Redis queue so sub-agents run in separate workers, avoiding recursive blocking. Results stream back via Redis Streams.

**Function parameter defaults** pre-fill values when an agent calls a function. Supports Jinja2 templates referencing the agent's input variables:

```json
{
  "email/send_email": {
    "sender": "{{company_email}}",
    "priority": "high"
  }
}
```

**User context in templates** — the calling user is always available as the `user` variable in system prompts and in function/query/connector parameter templates:

```jinja
You are assisting {{user.email}} from the {{user.custom_fields.department}} department.
Answer in the user's language: {{user.custom_fields.locale}}.
```

- `user.id` — user UUID
- `user.email` — user email
- `user.custom_fields` — the user's [custom fields](/admin/users-roles#custom-fields)

The `user` variable is platform-provided and overrides any same-named agent input variable, so locked parameters like `{{user.custom_fields.region}}` cannot be spoofed by the caller.
