Integration packages bundle agents, functions, skills, components, templates, and other resources into a shareable YAML file that can be installed with one click.

**How packages work:**

1. **Create**: Select resources from your Sinas instance → export as `SinasPackage` YAML
2. **Share**: Distribute the YAML file (GitHub, email, package registry)
3. **Install**: Paste/upload the YAML → preview changes → confirm install
4. **Uninstall**: Removes all resources created by the package in one operation

**Package YAML format:**

```yaml
apiVersion: sinas.co/v1
kind: SinasPackage
package:
  name: crm-integration
  version: "1.0.0"
  description: "CRM support agents and functions"
  author: "team@company.com"
  url: "https://github.com/company/sinas-crm"
spec:
  variables: [...]     # Install-time configuration (optional)
  agents: [...]
  functions: [...]
  skills: [...]
  connectors: [...]
  components: [...]
  templates: [...]
  queries: [...]
  collections: [...]
  stores: [...]
  webhooks: [...]
  schedules: [...]
  manifests: [...]
  databaseTriggers: [...]
  dependencies: [...]
```

**Key behaviors:**

- Resources created by packages are tagged with `managed_by: "pkg:<name>"`
- **Detach-on-edit**: Editing a package-managed resource clears `managed_by` — the resource survives uninstall
- **Uninstall**: Deletes all resources where `managed_by = "pkg:<name>"` + the package record
- **Upgrade**: Re-installing an existing package updates its resources in place (idempotent apply)
- **Excluded types**: Packages cannot include users, LLM providers, database connections or package repositories (these are environment-specific). A package can define roles but never assign them.
- **Dependencies**: Packages can declare Python dependencies — these are recorded in the database and installed in containers on worker restart

## Package repositories

A **package repository** is a place Sinas finds packages: the official one maintained by the Sinas team, or your own. Add repositories under **Packages → Repositories**. **Add official repository** adds [sinas-platform/packages](https://github.com/sinas-platform/packages) in one click. Then:

- **Browse and install:** **Packages → Catalog** lists every package your repositories offer. Install goes through the same preview and variables as a pasted package.
- **Updates:** an installed package shows **Update available** when its repository publishes a newer version. Updating installs the new version over the old one (an upgrade), after the same preview.
- **Nothing installs or updates on its own.**

Sinas fetches each repository's index when it is added, when you click **Refresh**, and every `PACKAGE_REPOSITORY_REFRESH_HOURS` (6) after that. This needs outbound HTTPS from the Sinas server. If a refresh fails, the error is shown on the repository and the last good index stays in use.

**A repository is a URL serving `index.json`.** The index lists each package's name, version, the path of its `package.yaml` relative to that URL, and the file's SHA-256:

```json
{
  "schema": "sinas.package-index/v1",
  "packages": [
    {"name": "github", "version": "0.1.0", "description": "GitHub integration",
     "path": "packages/github/package.yaml", "sha256": "…"}
  ]
}
```

A GitHub repository URL (`https://github.com/<owner>/<repo>`, optionally `/tree/<branch>/<folder>`) is read from `raw.githubusercontent.com`; any other URL is the base the index and paths are under. A package file that doesn't match its index checksum is refused. [sinas-platform/packages](https://github.com/sinas-platform/packages) shows how to generate the index (`scripts/build_index.py`).

**Private repositories:** set `auth` to send a token, kept in a shared [Secret](/build-resources/secrets), with every request. `bearer` sends `Authorization: Bearer <value>`; `header` sends the value in the header you name. Credentials never go in the URL.

```yaml
packageRepositories:
  - name: sinas-official
    url: https://github.com/sinas-platform/packages
  - name: internal
    url: https://packages.internal.example.com/sinas
    auth: {type: bearer, secret: PACKAGES_TOKEN}
```

**API:**

```
GET    /api/v1/package-repositories                 # List, with refresh state
POST   /api/v1/package-repositories                 # Add (fetches the index)
POST   /api/v1/package-repositories/official        # Add the official repository
PUT    /api/v1/package-repositories/{name}          # Update
DELETE /api/v1/package-repositories/{name}          # Remove (installed packages stay)
POST   /api/v1/package-repositories/{name}/refresh  # Fetch the index now
GET    /api/v1/packages/catalog                     # Packages on offer, installed versions, updates
POST   /api/v1/packages/install  {"repository": "sinas-official", "package": "github"}
```

`GET /api/v1/packages` and `GET /api/v1/packages/{name}` include `source_repository`, `latest_version` and `update_available`. A package installed by pasting its YAML follows the first repository that offers a package by its name.

Repositories are admin-only: `sinas.package_repositories.{create,read,update,delete}:all`. Installing from one needs `sinas.packages.install:all`, like any install.

## Installing a package more than once

Some packages describe a service that an instance may run several of: two Google Drive accounts, a work and a personal records store. Such a package declares `multiInstance: true` and uses `${{ install.name }}` wherever uniqueness matters — namespaces, role names, permission keys, published info:

```yaml
package:
  name: records
  version: "0.1.0"
  multiInstance: true
spec:
  variables:
    - { name: RECORDS_URL, type: text, required: true }
  connectors:
    - namespace: ${{ install.name }}
      name: api
      baseUrl: "${{ vars.RECORDS_URL }}"
  roles:
    - name: ${{ install.name }}-reader
      permissions:
        - { key: "${{ install.name }}.*.read:all", value: true }
  manifests:
    - namespace: ${{ install.name }}
      name: ${{ install.name }}
```

Install it under an install name (`instance`); `${{ install.name }}` is substituted before anything else, so it may also appear inside variable defaults:

```bash
POST /api/v1/packages/install   { "source": "...", "instance": "records-personal", "variables": {...} }
```

Each install is its own package record, named after the install name and tagged `managed_by: "pkg:<install name>"`, so upgrade (re-install under the same name) and uninstall work per instance. `package_name` keeps the declared package name. Without `instance` the package installs under its own name, exactly as a single-instance package does.

Guard rails:

- A package without `multiInstance: true` refuses any `instance` other than its own name.
- A `multiInstance` package that never uses `${{ install.name }}` refuses a second name, because both installs would create the same resources and take them over from each other.
- An install name already used by a different package is refused.
- Install names are lowercase letters, digits and dashes.

The console shows an *Install as* field on the preview of a multi-instance package; the package agent tools (`sinas_package_preview`, `sinas_package_install`) take `instance` the same way.

## Install-time Variables

Packages can declare typed variables that are prompted during installation. Variables are substituted into the YAML before resources are persisted — the resulting resources contain literal values, no runtime template evaluation.

**Declaring variables:**

```yaml
spec:
  variables:
    - name: APP_URL
      type: text
      description: Base URL where the app is reachable from containers
      example: http://host.docker.internal:8080
      required: true

    - name: PRIMARY_LLM
      type: resource_ref
      resource: llm_providers
      description: LLM provider for capable agents
      required: true

    - name: CHEAP_LLM
      type: resource_ref
      resource: llm_providers
      description: LLM provider for filtering/extraction agents
      required: true

    - name: ENABLE_LOGGING
      type: boolean
      default: false
      description: Enable verbose logging in functions

    - name: API_KEY
      type: secret
      description: External service API key
      required: true
```

**Variable types:**

| Type | Description | Validation |
|---|---|---|
| `text` | Free text input | Optional `pattern` (regex) |
| `boolean` | True/false toggle | — |
| `enum` | Fixed choices | `choices: [a, b, c]` |
| `resource_ref` | Pointer to existing resource | `resource: llm_providers\|database_connections\|collections\|secrets\|roles` — validated at install |
| `secret` | Masked input, stored encrypted | Creates/upserts a Secret. Not re-prompted on upgrade if already exists. |

**Substitution syntax:**

Use `${{ vars.NAME }}` anywhere in the package spec. Resolved by simple string replacement before parsing — not Jinja2, so no conflicts with system prompt templates.

```yaml
connectors:
  - baseUrl: "${{ vars.APP_URL }}"

agents:
  - llmProviderName: "${{ vars.PRIMARY_LLM }}"
```

**API:**

- `POST /api/v1/packages/preview` — response includes `variables` (declarations) and `requires_input` (bool). Pass `variables: {NAME: value}` in the request to preview with substitution.
- `POST /api/v1/packages/install` — pass `variables: {NAME: value}` in the request. Required variables must be present.

**Stored values:**

Variable values from the last install are stored in `Package.values`. On upgrade, the console pre-fills the form with previous values. Secret values are stored as `"***"` — the actual credential lives in the Secrets table.

**Endpoints:**

```
POST   /api/v1/packages/install       # Install package from YAML
POST   /api/v1/packages/preview       # Preview install (dry run)
POST   /api/v1/packages/create        # Create package YAML from selected resources
GET    /api/v1/packages               # List installed packages
GET    /api/v1/packages/{name}        # Get package details
DELETE /api/v1/packages/{name}        # Uninstall package
GET    /api/v1/packages/{name}/export # Export original YAML
```

**Creating a package from existing resources:**

```bash
curl -X POST https://yourdomain.com/api/v1/packages/create \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "my-package",
    "version": "1.0.0",
    "description": "My integration package",
    "resources": [
      {"type": "agent", "namespace": "support", "name": "ticket-bot"},
      {"type": "function", "namespace": "support", "name": "lookup-customer"},
      {"type": "template", "namespace": "support", "name": "ticket-reply"},
      {"type": "schedule", "namespace": "default", "name": "daily-digest"}
    ]
  }'
```

Supported resource types: `agent`, `function`, `skill`, `connector`, `manifest`, `component`, `query`, `collection`, `store`, `template`, `webhook`, `schedule`, `database_trigger`.
