## Context

MCP 2026-07-28 made the protocol stateless: no `Mcp-Session-Id`, no
`initialize` handshake, every request carries its own version and client
capabilities. The MCP client already speaks it (the Python SDK negotiates
2026-07-28 and falls back to handshake-era servers), and its one connection
per call fits the stateless model exactly.

Long-running work moved to the **Tasks extension**
(`io.modelcontextprotocol/tasks`, spec in modelcontextprotocol/ext-tasks).
A client declares it in each request's `_meta` capabilities. The server may
then answer `tools/call` with a `CreateTaskResult` (`resultType: "task"`)
instead of the tool's result. The client polls `tasks/get` until the task is
`completed`, `failed` or `cancelled`. While it is `input_required`, the
client answers its `inputRequests` with `tasks/update`, and it can send
`tasks/cancel` at any time. Clients should keep task ids durably so polling
survives a restart.

Without the extension, a server with long-running tools must either hold
the HTTP request open (and hit every timeout on the way) or refuse the
client. The SDK provides the declaration and result-claim hooks, but no
Tasks client.

## Decision

### Protocol (mcp_client)

Every connection carries a `ClientExtension` declaring Tasks, with a result
claim for `resultType: "task"`. The claim's resolver polls the task inline,
honouring `pollIntervalMs` (bounded to 0.2–5 s), for up to a wait the
caller chooses:

- terminal in time → what the original call would have returned
  (`completed`: its `result`; `failed` / `cancelled`: an error result), and
  the call looks like any other;
- still `working` after the wait, or `input_required` (that needs the agent
  or the user) → the resolver raises `TaskPending` with the latest state,
  and `call_tool` returns the `TaskState`.

`tasks/get`, `tasks/update` and `tasks/cancel` are sent through the SDK
session with typed request models whose `name_param` puts the task id in
the `Mcp-Name` header, which the spec requires for routing. The SDK ships
task types only for the 2025-11-25 revision, so the 2026-07-28 shapes are
defined here.

The extension only applies to 2026-07-28 connections: the SDK advertises a
claim-bearing extension only at protocol versions where its claim is
active. Handshake-era servers never see it, and the 2025-11-25
experimental tasks are not supported.

### Kept tasks (mcp_tasks)

An MCP tool call in a chat waits inline for at most
`mcp_task_inline_wait_seconds` (20), and never longer than the server's
`timeout_seconds`. A task still running after that is written to
`mcp_tasks` and the agent gets
`{task_id, status, hint}`. The agent then carries on or ends its turn,
exactly as with `run_in_background`.

The agent worker runs `poll_mcp_tasks_job` every 5 seconds (`unique=True`).
It claims due rows with `FOR UPDATE SKIP LOCKED` and a two-minute lease,
then polls them concurrently (bounded). Each task is polled at its own
interval: the server's `pollIntervalMs` within
[`mcp_task_min_poll_seconds`, `mcp_task_max_poll_seconds`].

- **Finished:** the result is mapped like any MCP tool result. Binary
  content goes to the chat's workbench when the agent has one. It is stored
  on the row and delivered with `chat_wakeups.deliver_to_chat` as
  `[mcp task <id> completed: <server>/<tool>]`, clipped like a background
  job result. Only whoever sets `finished_at` under the row lock queues
  that delivery, so a sweep, a status call and a cancel racing never
  produce two.
- **Input required:** new request keys are delivered once, as
  `[mcp task <id> needs input: …]`. The agent answers with
  `mcp_task_respond`; responses go out with `tasks/update` and only
  outstanding keys are accepted. Polling continues meanwhile.
- **Unreachable:** backoff (`min_poll · 2^n`, capped). After
  `mcp_task_max_poll_failures` consecutive failures the task is delivered
  as failed.
- **Expired** (past the server's `ttlMs`, or `mcp_task_max_age_seconds`
  when it gives none), the server removed or inactive, or the user no
  longer allowed to read it: the task is delivered as failed.

**Every poll decides under the row lock.** The server is asked first,
without holding anything. The row is then locked and re-read, and the
answer is applied only if the task is still unfinished. A poll that comes
back after a cancel or a response changes nothing.

**Deliveries go through an outbox** (`pending_deliveries`). A message is
written in the same commit as the state change it reports, and leaves the
outbox in the same transaction that writes it into the chat.
`deliver_to_chat` (and `inject_user_message`) take a `guard` that runs in
the delivery's transaction and commits with it; returning False withdraws
the delivery. The guard locks the chat row, then this row (the order a
chat deletion takes them), and takes the message off only if it is still
first in the outbox. So:

- a message is delivered exactly when it leaves the outbox;
- two flushes racing can't both send it, because the second finds it gone;
- a cancel that empties the outbox before the delivery commits means the
  message is never sent, and one that comes after is a cancel of an
  already-delivered question;
- no lock is held across an await outside the database. Every wait is one
  PostgreSQL can see, so a conflict with chat cleanup is a detected
  deadlock and a retry, not a stall.

A delivery the chat refuses for good (an archived chat, an inactive owner,
a hook that blocks it) is dropped from the outbox. One that raises stays,
and the sweep retries it every 30 s. One that was taken off and then failed
(the new turn could not be queued) is put back at the front.

**The inline wait is a hard bound.** Each `tasks/get` during it is limited
to the time left. A failed or slow look hands the task on, with its last
known state, to the background poller, instead of losing a handle the
server is already working on.

Polls act as the chat's user, through the API key the calling turn used
(stored on the row and bound around the poll). The server access check and
credential resolution therefore hold the poll to the same grants and the
same Secret as the call.

The agent sees this row's id, never the server's task id: the spec allows
servers to use task ids as bearer tokens.

### The agent's tools

Offered whenever the agent has an MCP server bound, as `tool_type:
"mcp_task"` system tools:

- `mcp_task_status`: a live `tasks/get`. If the task finished, the result
  is returned here and nothing is delivered.
- `mcp_task_respond`: `tasks/update`.
- `mcp_task_cancel`: `tasks/cancel`, best effort. Sinas stops following
  the task either way. Cancellation is cooperative, so the server may
  still finish.

`list_wakeups` lists the chat's running tasks. The way-of-working skill
teaches the `[mcp task …]` deliveries.

### Outside a chat

A call with no chat has nowhere to deliver a later result. It waits up to
the server's `timeout_seconds`; a task still running is then cancelled and
the call fails with a message saying so.

## Consequences

- Long MCP operations (CI runs, exports, approvals on the server's side)
  no longer time out or hold an agent worker: they behave like background
  jobs.
- The worst-case delay from a task finishing to its result arriving is
  its poll interval plus the 5-second sweep. Short tasks never notice,
  because they finish within the inline wait.
- Input requests go through the agent. The spec asks hosts to apply the
  elicitation trust model to them: the agent is instructed to ask the user
  when a request is meant for them, and `mcp_task_respond` can be gated by
  the agent's `toolApprovals` like any tool.
- Deleting a chat deletes its tasks without cancelling them on the server.
- `notifications/tasks` (push instead of poll, over `subscriptions/listen`)
  is not used: connections are per call, and polling is the spec's default.

## Alternatives considered

- **Suspend the round on a deferred completion** (as `run_in_background`
  with `wait: true` does). That suspension is decided before the call, but
  whether a call becomes a task is the server's decision, made per request
  after the call has started. A late suspension would mean rebuilding the
  round's checkpoint after execution. Delivering into the chat gives the
  same result, and the agent stays free.
- **Poll until done inside the tool call.** Holds the turn and a worker
  for as long as the task runs, and dies with the tool timeout: the problem
  Tasks exist to solve.
- **Keep the connection or session open.** 2026-07-28 removed sessions;
  task ids are the durable handle.
